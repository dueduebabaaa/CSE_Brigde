# BRIDGE — 컴퓨터학부 공고 자동 수집 시스템 설계서 (CRAWLING.md)

## 1. 개요 및 수집 대상
- **수집 대상 사이트**: 경북대학교 컴퓨터학부 공식 홈페이지 (`https://computer.knu.ac.kr/`)
- **수집 대상 게시판**: 공개 공지사항 게시판 (학부 공지, 학부 행사 및 대외활동)
- **실행 환경**: Node.js 서버 환경 (GitHub Actions / 서버리스 워크플로), **프론트엔드 환경 실행 절대 금지**
- **담당자**: 팀원 B (백엔드 / 크롤링)

---

## 2. 수집 원칙 및 보안/윤리 가이드라인

> [!IMPORTANT]
> **크롤링 실행 전 준수 사항**
> 1. 실제 학부 홈페이지의 `robots.txt` (`https://computer.knu.ac.kr/robots.txt`) 및 홈페이지 이용약관을 사전에 점검하고 허용된 범위 내에서만 수집합니다.
> 2. 실제 학부 홈페이지 접근 정책 및 게시판 구조를 확인하기 전에는 **절대로 무단 대량 크롤링을 실행하지 않습니다.**
> 3. 로그인 또는 학사 인증이 필요한 비공개 정보는 일체 수집하지 않습니다.

### 2-1. 수집 기술 우선순위
1. **공식 API 또는 RSS Feed 우선 활용**: 학부 홈페이지에서 RSS 피드나 오픈 API를 제공하는지 우선 점검합니다.
2. **Node.js + Cheerio 기반 정적 HTML 파싱**: RSS/API가 부재한 경우, 서버 부하가 가장 적은 Cheerio 정적 HTML 파서 라이브러리를 사용합니다.
3. **요청 제어 (Rate Limiting & Throttling)**: 요청 간격은 최소 2~3초 이상의 지연(Delay)을 두어 학부 서버에 과도한 부하가 발생하지 않도록 제어합니다.

---

## 3. 선별 필터링 및 데이터 무결성 규칙

### 3-1. 공모전/대외활동 선별 알고리즘
- 학부 공지 중 학생들의 대외 프로젝트 및 협업과 직결된 공지만 추출합니다.
- **포함 키워드**: `공모전`, `대외활동`, `해커톤`, `경진대회`, `서포터즈`, `아이디어톤`, `챌린지`, `부트캠프`, `특강`, `산학협력`
- **제외 키워드**: `등록금`, `수강신청`, `전과`, `휴학`, `복학`, `성적`, `졸업사정`, `장바구니`, `교직`, `예비군`

### 3-2. 중복 방지 및 수정 공고 업데이트 (Upsert)
- 공고 게시글의 고유 번호(`wr_id` 등)를 추출하여 `source_post_id`로 저장합니다.
- 이미 데이터베이스에 존재하는 `source_post_id`인 경우, 공고 수정일자(`updated_at`)를 비교하여 변경 사항이 있을 때만 UPDATE를 수행합니다.

### 3-3. 미확인 정보 처리 규칙
- 본문에서 공모전 마감일을 파싱할 수 없거나 명시되지 않은 경우, **임의의 날짜를 절대 생성하지 않습니다.**
- `deadline: null`, `application_start: null`로 저장하며, `status: 'needs_confirmation'`(확인 필요) 상태로 저장합니다.

### 3-4. 저작권 보호 및 링크 제공
- 공지사항 본문 전체나 첨부파일을 무단으로 데이터베이스에 긁어오지 않습니다.
- 2~3줄 분량의 핵심 요약과 키워드 태그만 생성하고, 상세 내용은 **학부 원본 공지 링크(`sourceUrl`)** 및 **주최측 공식 접수 링크(`applicationUrl`)**로 이동할 수 있도록 아웃링크를 제공합니다.

---

## 4. 장애 대응 및 대체 구조

### 4-1. 실패 시 데이터 보존
- 크롤러 실행 중 네트워크 오류나 사이트 일시 점검 등으로 수집이 실패하더라도, **기존에 저장된 공고 데이터베이스를 절대 삭제하거나 덮어쓰지 않고 안전하게 유지**합니다.
- 실행 결과는 즉시 `crawling_logs` 테이블에 성공/실패 여부, 신규 수집 건수, 에러 메시지를 기록합니다.

### 4-2. 관리자 직접 등록 대체 (Fallback)
- 학부 홈페이지 구조 개편 등으로 크롤러가 일시 중단된 경우에도 플랫폼 운영이 지속될 수 있도록, 관리자가 관리자 페이지(`/admin/opportunities`)에서 직접 공고를 등록(`source_type: 'admin_manual'`)할 수 있는 대체 수단을 보장합니다.

---

## 5. 자동 실행 및 워크플로 아키텍처

```
[GitHub Actions Scheduled Cron (매일 00:00 KST)]
                   │
                   ▼
  [scripts/crawler/index.ts 실행 (Node.js + Cheerio)]
                   │
  ┌────────────────┴────────────────┐
  │ 1. KNU CSE 공지 게시판 HTML 수집 (Throttling 적용)
  │ 2. 키워드 필터링 (공모전/해커톤만 선별)
  │ 3. source_post_id 중복 검사
  │ 4. 마감일/주최기관 추출 (미확인 시 null)
  └────────────────┬────────────────┘
                   │
                   ▼
 [Supabase opportunities 테이블 Upsert (Service Role Key)]
                   │
                   ▼
 [crawling_logs 테이블에 실행 결과 기록]
```

### 5-1. 실행 트리거 방식
1. **정기 자동 수집**: GitHub Actions Cron 스케줄 (`cron: '0 15 * * *'` - UTC 15:00 = KST 00:00)
2. **수동 즉시 수집**: GitHub Actions `workflow_dispatch` 또는 관리자 페이지 버튼 클릭 트리거

### 5-2. 비밀 키 보안 원칙
- 크롤러가 Supabase에 공고 데이터를 직접 등록할 때 사용하는 `SUPABASE_SERVICE_ROLE_KEY`는 **GitHub Actions Repository Secrets**에만 보관하며, 프론트엔드 코드나 Git 저장소에는 절대 커밋하지 않습니다.
